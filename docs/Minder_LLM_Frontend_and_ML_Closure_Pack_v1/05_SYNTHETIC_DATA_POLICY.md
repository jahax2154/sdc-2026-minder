# Synthetic data — purpose, evidence boundary and evaluation

## Decision analysis
Synthetic data is useful for software testing, simulation, training experiments and, where validated,
augmentation of a real dataset. Permission to use it and disclosure do not establish empirical truth.

For Minder, synthetic generation can expand tested conditions and unblock reproducible experiment
execution. It cannot create observed evidence for unmeasured roles, independent national demand
counts, or genuinely observed historical quarters.

An example:
If we assume a role grows 10% per quarter and generate many records following that assumption,
a model that predicts 10% has learned the assumed world. It has not measured Malaysia's market.
This remains true when a pretrained LLM supplies the assumed pattern.

## Three separate data classes
| Class | Meaning | Permitted use now |
|---|---|---|
| Observed | Acquired records/official published statistics with actual scope and provenance | Normal evidence-backed recommendations within supported meaning |
| Model-estimated/imputed | Values inferred from observed data plus explicit assumptions | Separate research output; no automatic production activation |
| Synthetic/scenario | Generated records for specified assumptions/test conditions | Isolated development, simulation and experiment demonstrations |

Do not call all inferred data "observed". Matching an aggregate total does not identify the distribution
of detailed roles or the time dynamics within it. Do not copy a source URL onto simulated cells as if
the publisher reported them.

Potential future augmentation:
Fit/calibrate using representative permitted observations, evaluate real-only versus real-plus-
synthetic on an untouched real holdout, check coverage/bias/privacy, and retain improvements only
for the demonstrated task/scope. This is conditional, not a claim about the current dataset.

## Scope for the deadline
Use the existing real data for normal recommendations, with source granularity and missingness.
Use B's synthetic scenarios to test/train the implemented pipeline and prepare real RunPod execution
where separately authorized. Real market forecasts remain unavailable without compatible history.

Do not fabricate missing evidence for the other 900 personal-only results.
Keep all supported roles explorable. A may show broader sourced context with precise wording;
that is different from giving every role a synthetic demand score.

No new end-user scenario feature is required by this pack.
If simulation is demonstrated, use an explicitly separate mode with persistent visible labelling:
"Simulated scenario — generated assumptions, not observed Malaysian demand."
The label must survive API response, chart/export, model output and LLM explanation, not only appear
in a pitch slide. Normal runtime must not silently mix scenario data with market evidence.

## Evaluation rules
- State the target and label origin before training.
- Split real/source groups before generator fitting/augmentation; preserve chronological boundaries.
- Keep correlated variants from a common source/group together.
- Train/validation/test generated by the same process are synthetic evaluation even when seeds differ.
- Test across assumptions/scenario families to reveal simulation brittleness.
- Compare real augmentation on an untouched real holdout if available; otherwise don't claim benefit.
- Fitting synthetic trend labels is not independent forecast validation.
- Fitting A's scoring formula is not independent career-fit validation.
- Report source coverage and scenario coverage as separate metrics.
- Synthetic-only metrics cannot promote a model into normal real-market serving under this pack.

## Privacy and licensing
Fully fictional aggregate scenarios avoid processing actual user records for this purpose.
Data derived from personal records is not automatically anonymous simply because it is synthetic.
Do not reproduce private CVs, personal contacts, restricted records or near-identical data rows.
Respect source reuse conditions; synthesis is not permission to bypass them.

## Minimal submission disclosure
For a completed experiment, fill actual values into:
"We use [named observed sources] for current market context. Separately, [generator/version]
produced [scenario types/counts] to evaluate [specific pipeline behaviour]. [models] were compared
against [baseline] on [split]. These results measure [simulation performance/policy imitation].
They do not establish real Malaysian forecast accuracy. [actual forecast availability] remains
limited by [specific history issue]."

Report actual training location, job IDs/cost, model version and whether the runtime model changed.
Do not claim RunPod training, independent accuracy or a completed forecast merely from prepared code.

## Primary methodological references
ONS synthetic data policy:
https://www.ons.gov.uk/aboutus/transparencyandgovernance/datastrategy/datapolicies/syntheticdatapolicy
ONS explains that suitability depends on intended use and that synthetic records do not preserve
all real-data properties. This is methodological guidance, not Malaysian legal authority.

ONS evaluation discussion:
https://datasciencecampus.ons.gov.uk/evaluating-synthetic-data-using-synthgauge/
Useful for distinguishing task-specific utility from a universal "good synthetic data" label.

scikit-learn data leakage guidance:
https://scikit-learn.org/stable/common_pitfalls.html
Fit preprocessing on training data; information unavailable at prediction time cannot be used to
construct an honest held-out evaluation. Apply this principle to generator fitting as well.

NIST synthetic data privacy discussion:
https://www.nist.gov/blogs/cybersecurity-insights/differentially-private-synthetic-data
Synthetic generation alone does not provide a formal privacy guarantee.
