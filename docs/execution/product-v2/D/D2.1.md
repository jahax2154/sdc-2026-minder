# D2.1 — direction and task/progress first slice

Status: passed for implemented operations; limited for automatic preparation generation.
Branch: session/d-profile-state. Dependency: D1 d887de3d7ba64541bfbb9d4ecfd3e7e73bb1b417.

Implemented registry operations: GET/PUT /api/product/direction,
POST /api/product/tasks, POST /api/product/task-action, GET /api/product/progress.
Requests follow A-published DirectionWrite, TaskCreate, TaskAction. Direction PUT
returns the persisted direction document; GET returns {direction:document|null}.
Task writes return {plan:PlanProgress,feasibility:{status,...}} as C services do.
Direction selects only a registered role and optional owned matching plan; no
implicit plan creation. Existing /pathway-preview and POST /plans remain the
explicit preparation flow. Select its returned plan_id with another versioned PUT.
Switching role preserves every historical plan. Requirements remain not_evaluated
until consumers call actual requirements/assessment services.

Task actions: edit(title/description/estimated_hours); reschedule(scheduled_at,
optional estimated_hours, null unschedules); complete; undo; cancel. Undo returns
completed activity to proposed, preserving its old schedule as metadata and mastery
unchanged. Completed/locked tasks remain immutable outside explicit completion undo;
completed descendants prevent prerequisite undo. Cancelling active prerequisites is
rejected. Manual tasks start proposed/scheduled and cannot mint assessed mastery.
Task skill/evidence/resource references are checked against runtime catalogues/profile.

All mutations bind the exact request body/path to one owner/idempotency key.
Retries return the original result (which can now be an old version: refetch after
retry); changed scope fails409. Stale versions fail409, inaccessible owned targets
fail404, invalid fields/references fail422 or unknown resource404. Events and direct
user authority are persisted in the same transaction. Proactive actions still use
C's proposal approval boundary; these handlers accept explicit UI writes only.

Read-only helper for E: minder_app.product_state.state_view(store, owner).
Owner must be the server-authenticated identity. Returns profile, profile_version,
direction, plans, active_plan, progress from one SQLite read transaction. It never
writes/migrates or changes state. Product runtime migrates at startup; direct
Application tests lazy-initialize migration5 before product writes.

Canonical progress object: status(available|empty), plan_id, state_version,
completed_count, eligible_count, cancelled_count, fraction(number|null), observed_at,
denominator. Denominator counts every non-cancelled task once in chosen active plan;
prerequisite edges are dependencies, not containers. No tasks/selection => empty,
counts0/fraction null. Counts measure activity, never evidence/skill readiness.

Checks: 14 focused unittest tests passed (test_profiles, test_plans,
test_product_migrations, test_product_state). Covers refetch/restart, C direct-action
completion against same record, duplicate requests, changed retry scope, stale
