## Versioned policy and executable verification

Policy file `apps/backend-api/data/llm-behaviour.v1.json`, ID `minder-grounding-privacy-v1`, is loaded by `minder_app.grounding` and identified in the chat response/persisted evidence ledger and shared worker rules. This is application behavior, not scoring policy. The model selects opaque evidence IDs via the existing `statement_ids` function parameter; it cannot author factual prose, URLs, quantities, score values or action-success fields. The backend renders passages and resolves source URLs/metadata from its owner-scoped stored records.

A valid ID alone is insufficient. For the current supported source, the backend validates typed MarketResult, exact unique inspected row IDs, row country/entity membership, source cohort hash, source universe, observation/publication/availability/ingestion dates and denominator. It checks the stored supporting passage against the same deterministic rendering and checks a claim's text, category, date/status metadata and citation bindings. A count-changing claim, unrelated source URL/passage, national-scope substitution or altered date fails. Available claims are derived inspected-record measurements, **not quotations from the linked careers landing page**; claim metadata identifies this. Listed ads do not establish current vacancies, hires or national/quarterly demand.

Arbitrary article/document/LLM factual claims have no supported template and are not displayed. Missing support becomes an app-authored limitation/focused question; unavailable forecasts remain unknown, not zero. Personal assessments are checked against the actual backend assessment/status but no numeric index is sent/rendered in chat. Self-reported activity counts, calculated assessments and proposed/unexecuted actions have separate categories. The model never produces action confirmation. Action controls/history continue to use persisted executor results; a failed write cannot produce an applied audit/notice.

On malformed/unverifiable model output: discard it, return verified stored statements and explicit limitations, mark provider response rejected. Zero semantic repair retries; existing provider defaults allow one transient network retry (bounded timeout, token and daily/concurrency caps). Model or document instructions cannot change this behavior, the allowed function schema or authority checks. Worker invalid selection retains its existing labelled deterministic prevalidated proposal fallback; it cannot execute a proposal.

Automated-check limitations: this is a deliberately closed claim vocabulary with exact passage/structured-derivation verification, **not general natural-language entailment, source truth/freshness verification, validated skill mapping or independent causal/career accuracy**. It cannot prove that an employer is actively hiring, that a source classification is correct, that the inspected population covers Malaysia, or that a user statement establishes competence. C uses the current concrete B source_facts/snapshot boundary; unsupported adapters or available forecasts without a compatible supporting derivation produce limitations. C-006-GROUNDING-INTERFACES.md requests a future A-owned reusable passage/derivation contract; no shared schema was changed. Broader free-form grounded prose requires an explicit supported claim interface and evaluation, not weaker citation checking.

## Actual personal-data flow, minimisation and retention

- Browser -> local API: authenticated JSON profile, explicit edits, UTF-8 text intake or question; bearer capability and selected role are in sessionStorage. Local HTTP is loopback; no production identity, HTTPS, token expiry/recovery or consent/compliance claim.
- Intake/profile state: raw text drafts, canonical evidence/preferences/constraints and historical versions remain in local SQLite; document claims stay distinct from reviewed competence. New privacy refinement does not delete or rewrite existing records.
- API -> Groq: versioned policy, best-effort-redacted bounded question, bounded opaque evidence IDs/categories/canonical passages and local function schema. No full profile/CV, complete plan graphs, owner/profile/plan/task/version identifiers, citation URLs/hashes or ordinary ranking values are automatically sent. Progress counts are included only for progress/task/roadmap questions. Worker sends candidate index/operation/constraint-checked flag/proposed day, not executor target IDs, state versions, raw diffs, reasons or evidence IDs. Public role/topic identifiers and source-backed quantities/dates remain when needed. Personal questions/narrative and proposed schedule day can still be personal data; contact/key/link regex redaction is not complete anonymisation or DLP.
- Groq -> API: one native selection request's arguments, validated by tool JSON schema and application ledger. Raw model prose/claims/URLs/action assertions are discarded. The API resolves public citations locally. It does not use remote MCP, built-in browsing, external messaging or external mutation tools.
- New chat storage: bounded owner-scoped `grounding` ledger with policy/profile version, canonical claims, inspected-row derivation IDs and only used source records. No new full `context` profile/recommendation/plan duplication or raw chat question/response transcript is stored. Existing old `context` records, profiles/drafts/history/actions/events/notices/quota records persist unchanged. **No automatic expiry/purge or account deletion API exists**; state remains until deliberate operator/database handling. No retention duration is promised. Backups/exports are not newly created by this task.
- Local persistence is plaintext SQLite, not encryption at rest. Audit found DB/WAL/SHM mode 0644; this refinement restricts owned regular DB/WAL/SHM files to 0600 on connection without record deletion. Verified on the actual C files after restart and by a temporary-DB no-data-loss test. OS/account/backup access is outside this application's user isolation; this is not a claim of production privacy readiness.
- Logs: tested dev.py uses QuietHandler on both listeners, suppressing request lines. Provider logs contain only local request ID, retry attempt and allowlisted token counts; tests verify no keys, headers, messages or response text. Error responses use safe codes/request IDs. This does not attest to host/proxy/OS logs or third-party logging; standalone default WSGI access handlers/integration hosting must be separately configured/reviewed. No secret values, file contents, environment dumps or auth headers are recorded in this report.

Provider configuration observed in code: HTTPS Groq chat-completions endpoint, selected model from the owner-only private loader/verified metadata, temperature 0, one forced nonparallel local function, default 512 output tokens capped at 1024, 12-second transport timeout, one transient retry, 32 KiB app context cap, two in-process concurrent slots and persisted configurable per-user UTC-day logical-call budget (default 20; each logical call may use its one transient transport retry). These are app guards, not verified account entitlements. Private configuration overrides are not printed. No provider account Data Controls/ZDR, training-use, regional settings or contractual/legal compliance was inspected or inferred from successful responses. General provider documentation: https://console.groq.com/docs/your-data. It describes controls/retention possibilities, not proof of this account's effective configuration; an authorised account admin must verify those settings separately.
