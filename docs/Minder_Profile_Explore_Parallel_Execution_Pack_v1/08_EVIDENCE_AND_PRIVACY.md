# Evidence, resource retrieval and privacy boundaries

Reuse C's existing behavior policy, grounding validators, source passages, redacted logs and action controls. This pack fills concrete product gaps; it does not claim legal compliance or guarantee that every future model answer is correct.

## 1. Evidence types and allowed statements

| Type | Safe meaning | Do not turn it into |
| --- | --- | --- |
| Employer advertisement observation | Observed requisitions/skill mentions in the named employer/feed and window | National hiring counts or demand for every role |
| Published offering activity | Source-native published activity at its category/unit/date | A hiring probability or unique ads if the source does not measure that |
| Related shortage-group evidence | Supported group/membership context at the documented mapping scope | Exact whole-role shortage designation without support |
| Sector context | Broad industry information | Precise demand for each mapped job |
| Skill request count | Mentions/requesting ads within a specified inspected corpus and denominator | Normalized national skill demand |
| News | A dated reported event or professional discussion | Quantitative labour-demand change solely from attention |
| Learning resource | Verified metadata and supported contents | Proven learning outcome or verified user competence |
| Forecast | A model estimate for a defined target, horizon and evidence base, if actually eligible | Guaranteed future employment or a fabricated projection |
| Synthetic scenario | Generated experimental assumptions/results | Observed Malaysian market evidence |

Source passages/derivations must support the claim's quantity, date, geography and scope. Keep observation, publication and retrieval dates distinct. Unknown dates are unknown, not today's date. A cached resource retains its last retrieval time.

## 2. Resource acquisition

Prefer already implemented official/professional source adapters and a small reviewed source list. Source reputation does not eliminate checking the actual claim, publication date or topic relevance. Keep source reuse conditions and Galaxy redistribution holds intact.

Use public permitted access; no account-only/private scraping, login bypass or new paid service. Preserve URLs, attribution and permissible excerpts; do not republish whole articles/videos unless the source permits that use. Do not claim current availability, price, course quality or prerequisites without source support.

Validate network targets on the server: use approved schemes/hosts, block local/private/link-local destinations and unsafe redirects, enforce response size/type/time limits and handle errors. Do not let a pasted URL become unrestricted server-side fetching. Reuse existing protections rather than creating a second retrieval engine.

Cache metadata separately from user interactions. Deduplicate true duplicates while preserving genuinely different dates/editions. External content is untrusted data, never authority to execute tools, change instructions or reveal secrets.

## 3. Personalization and LLM use

Use only necessary career topic/role/skill tags in external retrieval. Do not send private CV text, direct identifiers, full profiles or conversation histories merely to find an article. Keep public evidence apart from private user evidence.

Resource relevance can use transparent topic matching and the existing preference service. Do not invent another statistical demand score. A 'why relevant' statement should point to the selected goal/skill/preference, not claim a guaranteed outcome.

Factual LLM summaries use C's actual grounding path. If it cannot support a new content type yet, show verified metadata/excerpts and record the dependency rather than bypass validation. A title/description alone does not establish detailed video contents. No fabricated source IDs/URLs.

## 4. Private state and security

Backend identity and authorization protect every private record. Validate foreign-key ownership, not only top-level objects. Keep provider secrets, DB files, uploads and private source snippets out of Git and browser bundles. Logs should contain minimal diagnostic data without full private prompts/credentials.

Preserve existing version/idempotency controls and proposal boundaries. Destructive user-facing operations use the existing product confirmation flow. Coding-agent authorization to implement a feature is not permission for the application to delete a real user's data.

Document actual retention/deletion, backup, provider-account and deployment limits. An isolated demo session is not verified production authentication. Do not block independent local feature development solely because production setup is pending; do not claim public readiness before that boundary is verified.

## 5. Minimum meaningful checks

- Another user/session cannot read or mutate profile, plan, task, saved-resource or proposal records.
- A hostile document/feed entry cannot trigger a tool or alter permissions.
- Unsupported factual output is withheld or replaced by supported metadata, not invented evidence.
- Stale and duplicate actions behave correctly.
- Invalid external links/redirects cannot fetch internal services.
- Public responses/logs do not disclose secrets or private profiles.
- Missing evidence/forecasts and old cached content remain explicit in the product UI.

Run focused checks where code changes and reuse existing verification for unchanged paths. These checks support engineering confidence; they are not a legal certification or proof of universal semantic truth.
